架构说明/ NanoPi R76S/ 2026-10-22

event-agent三层架构与消息流转

一套跑在 ARM 单板机上的事件驱动系统：三个层次、九个进程， 所有进程用同一种消息说话。本文说明每一层有什么、进程之间怎么传消息、 一个事件从产生到执行要经过哪些人。

01

系统要做什么

系统里有一堆硬件进程在干活：读温度、控加热器、驱动电机。 它们不断产生事件——温度超了、电机到位了、某个进程掉线了。 系统需要决定这些事件该怎么处理，然后发出操作去执行。

传统的做法是写一张「事件 → 操作」的对照表，事件来了就查表。 这套系统要试的是另一种做法：把这张表交给大模型， 让它看着当下的事件和上下文，现场判断该做什么。 对照表还在，只是变成了给模型看的规则和建议，而不是唯一的答案。

所以整个系统的核心问题就一句话：怎么让一个只会读文字、写文字的模型， 安全地看到系统里发生了什么，并且真的把事做成。 三条答案，就是三个层次。

02

三层架构

三个层次按「谁更靠近物理世界」划分，不同的层有不同的限制条件： 底层要求时间确定，中层要求安全隔离，上层要求好用好改。

① 系统进程层：五个原生程序

这一层是普通的 Linux 程序，用 Rust 写成，装进 Docker 容器里跑。 它们负责和外部世界打交道——硬件、用户、云端模型——以及维护整个系统的秩序。

原生系统进程层 硬件、用户、云端模型的出入口

bus 是消息总线，也是唯一一个所有进程都要连的进程。 它给每个进程维护一个消息队列，负责把消息送到对的人手上， 顺便托管系统的「环境变量」——那些所有进程都关心的共享状态和历史数据。

hw-temp 是硬件进程，目前是温度模拟器：每秒算一次温度、 超阈值就发告警事件，对外提供「启动加热」「停止加热」「读温度」三个操作。 将来换真实传感器，只改它内部，外面不变。

web 是网页后端，也是系统和用户之间的翻译：外面的浏览器说普通 JSON， 系统里面说统一的消息格式，两边的话都由它转。

heartbeat 每两秒问一遍「谁还在」，发现进程掉线就发出事件—— 这是系统知道「哪里出问题了」的唯一来源。

llm-gw 是大模型网关。整个系统里只有它拿着云端模型的密钥， 也只有它会发起对外的 HTTPS 请求。

② AI 代理层：三个 Wasm 任务

这一层是系统的「思考」和「执行」部分，跑在 Wasm 沙盒里（WasmEdge，由 Docker 管理）。 沙盒意味着严格限制：不能开线程，不能自己上网，不能读文件， 只有一条到总线的连接。它们能做的事，仅限于总线上有的操作。

WasmAI 代理层 决定做什么，以及怎么做完

runtime 是事件运行时，系统的「大脑」。 它订阅所有事件，判断每个事件该怎么处理：有规则就用规则， 是用户在对话框里说的话就交给大模型推理，然后发出操作。 沙盒里没有别的进程能替它做这个判断。

task-thermostat 是恒温任务进程。 「保持 25 度」不是一个动作，而是一个要跑几十分钟的循环： 读温度、开或关加热器、再读温度。 这种活不能压在 runtime 身上，所以单独做成一个任务进程。

task-motor 是电机演示任务进程，同一类东西： 收到「让电机正转三圈再反转三圈」这样的指令后，自己编排步骤、 一步步调用电机操作，跑完报告结果。

runtimetask-thermostattask-motor

③ 实时进程层：一个实时程序

这一层只有一个进程，因为它没法待在容器里。 电机控制要求每 4 毫秒收发一次总线报文，任何一次调度延迟都可能让电机抖动甚至报错， 所以它需要操作系统的实时调度权限、需要独占总线网口、需要把内存锁住不被换页。 这些在容器里都做不到，于是它以普通系统服务的形式直接跑在板上。

实时实时进程层 确定性优先，不接受延迟

motor-ecat 守着一条 EtherCAT 总线，按固定周期驱动 MOONS 步进电机。 对外它提供「使能」「停止」「相对移动」「绝对定位」「设速度」这些操作， 用法和别的进程没什么不同——上层完全不必知道它是个实时程序。

它内部把自己分成两半：一半是那个雷打不动的 4 毫秒循环，只碰电机数据； 另一半负责收总线消息、回状态。命令进来放一个抽屉就返回， 循环自己在下个周期取走执行——实时的部分从不等人。

motor-ecat

三层之外还有两个角色：浏览器是用户界面， 云端大模型是推理引擎。它们都不在系统内部， 分别通过 web 和 llm-gw 这两个门进出。

03

九个进程一览

进程层形态它发什么它提供什么
bus系统容器—注册、环境读写、注册表查询
hw-temp系统容器温度快照、告警、告警解除加热器开关、读温度、设环境温度
web系统容器用户发来的对话回复对话
heartbeat系统容器心跳、进程上线/掉线—
llm-gw系统容器—调用大模型
runtimeAI 代理Wasm决策记录—
task-thermostatAI 代理Wasm任务开始/结束启动/停止恒温任务
task-motorAI 代理Wasm任务开始/结束电机往返演示

这张表的最后一列很重要：每个进程提供的操作，最终都会变成大模型手里的工具。 进程启动时把自己的操作名、一句中文描述和参数格式登记到总线上， runtime 拿来拼成给模型的工具清单。所以给系统加一个新硬件能力， 模型就自动学会用它，中间不用改任何代码。

04

消息怎么走

所有进程之间只有一条通道：连到 bus 的 TCP 连接。 没有谁直接连谁，没有中间件，也没有共享内存。 消息分两种，这也是整个架构里最要紧的一条规矩。

两种消息：事件和操作

类型是谁发的去哪会不会等回复例子
事件 任何进程 广播给所有关心它的人 不等 温度超过 60 度了
操作 需要别人做事时 只交给一个负责的进程 要等结果 把加热器关掉

一句话记住：事件是广播，谁爱听谁听；操作是点名，必须有人接。 事件丢了最多是少一次通知，操作没人接就是系统坏了——所以总线对这两种消息的待遇也不同： 队列满的时候先丢事件，操作不丢。

「点名」还带来一条约束：同一个操作只能有一个提供者。 第二个进程想提供已经有人认领的操作，注册时就会被拒绝。 这条看似苛刻的规则，保证了「谁负责」永远只有一个答案。

事件hw-temp 发出，所有订阅者收到
{"method":"event.temperature.alarm",
 "params":{"source":"hw-temp",
           "data":{"level":"high","value":61.4,"threshold":60}}}
操作runtime 请求，只有 hw-temp 会接
{"id":"runtime-17","method":"action.heater.stop",
 "params":{"source":"runtime","data":{}}}

返回：{"id":"runtime-17","result":{"heater_on":false}}

总线上怎么找到对的人

没有地址簿，靠的是方法名的前缀。方法名统一写成「类别.领域.名称」， 比如 event.temperature.alarm、action.heater.start。 进程注册时声明两件事：我关心哪一类事件（订阅），我负责哪一类操作（提供）。

  • event.temperature.* 表示「温度相关的所有事件」，在 web 这里就是它订阅的前缀。
  • action.heater.* 表示「加热相关的所有操作」，由 hw-temp 独自提供。
  • 发事件时匹配所有声明了这个前缀的进程，逐个投递；发操作时只找一个，找不到就回「没人负责」。

另外，每条消息的「发送者」字段由总线统一填写，进程自己说了不算。 否则任何进程都能冒充别人发事件。

三种跨越边界的连接

系统内部是一个样子，跨出边界就各有各的规矩。整个系统只有三处是这样：

两点之间用什么为什么是这样
浏览器 ↔ web WebSocket + 普通 JSON 浏览器不是系统进程，也没必要懂内部协议，所以由 web 负责翻译
Wasm 进程 ↔ bus 同一条 TCP 连接 沙盒里只允许这一条网络连接，其余一律不通，这是隔离的代价也是保证
llm-gw ↔ 云端 HTTPS 密钥和加密都只留在这一个进程里，沙盒接触不到

沙盒里的进程其实和原生进程用的是同一套消息、同一套接口， 换一种语言或换一个平台，业务代码几乎不用改。这是「所有进程说同一种话」 带来的直接好处。

05

两个完整流程

温度报警：一次广播，两条路

  1. hw-temp 算出温度越过了 60 度，状态从「正常」变成「高温」，发一次告警事件。
  2. 总线把这条事件广播给所有订阅者：web、runtime、heartbeat 都在其中。
  3. web 立刻把它翻成网页能懂的形式推给浏览器——这一路完全不经过 runtime， 所以大模型再慢也不影响用户看到告警。
  4. runtime 按规则判断高温要停加热器，发出「停止加热」这个操作。
  5. 总线找到唯一负责这项操作的 hw-temp，把请求投过去，再把结果回给 runtime。
  6. runtime 记一条决策事件，说明这次是规则处理的。全程没有调用大模型。

用户说话：一次推理，派一个任务

大模型在这里的角色很明确：它只负责选操作、填参数。 真正的执行者是 task-thermostat， 它拿到目标温度后自己跑循环，读温度、开关加热器，跑完发一条结束事件。

不用模型：外部程序也能直接控制电机

系统的控制面不只给大模型用。任何程序连上 web 的 WebSocket 端口，就能直接发控制命令，发完立刻拿到回执， 电机位置再从每秒一次的状态推送里读。

WebSocket任意客户端 → 设备 8090 端口
→ {"type":"control","cmd":"motor.move_rel","delta":-60000}

← {"type":"control_result","cmd":"motor.move_rel",
   "ok":true,"result":{"accepted":true}}

← {"type":"motor","state":{"axes":[
     {"axis":0,"position":86170,"velocity":0,"enabled":true,"reached":true}]}}

这一路完全不经过 runtime 和大模型。20000 个微步是一圈， 所以上面这条命令是「逆时针转三圈」，实测三秒左右到位。 它说明了一件事：模型是系统的一种使用者，不是必经之路。

06

为什么分成三层

把进程按层摆放，不是为了好看，而是因为三层面对的限制根本不同。

系统进程层要的是秩序。 谁在线、消息送给谁、共享状态存在哪、 密钥归谁保管——这些问题必须有一个确定的答案，而且必须随时可用。 所以这一层用普通程序，跑在容器里，随系统起来。

AI 代理层要的是安全。 这一层的代码是给 AI 写、也由 AI 改的， 可信度天然低一档。把它关进 Wasm 沙盒，关掉网络、线程和文件系统， 只留一条到总线的连接，它就算写错也伤不到系统。代价是它什么都要走总线， 但这也正好保证了「系统里发生的一切都看得见」。

实时进程层要的是时间。 这一层的成败以微秒计， 任何一层抽象、任何一次内存分配都可能让电机抖一下。 所以它不进容器、不用异步框架、不参与事件广播的节奏， 自己按时钟转，只在对外的接口上装作一个普通进程。

三层之间没有特殊通道，全部走总线。意味着越往上越自由、越往下越严格， 但彼此的边界始终是同一种消息——这正是这套架构能同时容纳 「大模型推理」和「4 毫秒闭环」的原因。
